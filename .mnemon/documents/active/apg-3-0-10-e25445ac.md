# 外部组件实测的宿主实务：无特权沙箱失效判别与低占用源码构建（APG 3.0.10）

**这是派生件，不是权威源。** 权威顺序：`decisions/0006-root-instruction-block-ownership.md` → `plans/MULTI_AGENT_INFRA_INTEGRATION_RESEARCH.md` §13.18 → 仓内代码与测试。冲突时以仓内为准。

本文**补充而非取代**既有的"外部组件预编译件安全校验规程"文档：那份的 §5 把无特权沙箱写成可用的隔离手段，本文记录它**会失效**、如何判别、以及失效时由谁报告。

## 1. 无特权沙箱会失效，而且很容易误诊

**症状**：仓库内的沙箱跑者（工作区内 `.agent-scratch/external-test/sandbox-run.sh`，非分发件）在真正执行前自检失败，**REFUSED** 退出。

**误诊诱因**：报错是 `unshare: 打不开 /proc/self/uid_map: 权限不够`，极易读成"内核禁止非特权 user namespace"。

**四步判别表**（逐步实跑，不要猜）：

| 测试 | 观测 | 含义 |
|---|---|---|
| `unshare -U true` | rc=0 | 建 user namespace **允许** ⇒ 不是内核禁 userns |
| `unshare -r true` | 打不开 `/proc/self/uid_map`（EACCES） | 卡在**写 uid 映射**这一步 |
| `unshare -m true` / `unshare -n true`（不带 userns） | EPERM | **正常现象，不是证据**——没有 userns 就没有 `CAP_SYS_ADMIN`，这正是要用 `-rmn` 组合的原因 |
| 同一命令在更宽的文件策略下重试 | `unshare -rmn` OK | **确证**根因在文件沙箱（Landlock 一类）拒绝写 `/proc/self/uid_map` |

**结论**：「能不能建 userns」与「能不能写 uid 映射」是两件事，失败点落在后者的**文件访问权限**上，与内核 namespace 支持无关。

**对既有记录的影响**：已提交的实测记录若把"执行只在无特权 namespace 内"写成无条件事实，那是**一次性测量**的描述，不是后续复跑能保证的性质。仓内 ADR 0006 已按此加限定。

## 2. 隔离降级必须显式报告（已修）

同一轮发现的**真缺陷**：`scripts/test-interop-writers.sh` 的 section D 原文是 `if unshare -rn true; then NET="unshare -rmn"; fi`——拿不到命名空间时**静默把隔离降成空**，随后照常打印 `0 failed`。也就是说，一批"全绿"的门禁结果可能是在**没有网络隔离**的条件下取得的，而输出里没有任何提示。

修法只加可见性、**不动断言与计数**：新增 `note_warn`，收尾多打一行 `section D isolation: …`。`N passed / N failed / N gaps` 的格式**故意保持不变**，这样此前各处引用过的数字继续有效。

**两条分支都要能验，且不该为此申请特权**：真环境下应出现 `WARN` + `NOT network-isolated`；把一个**空操作 `unshare`** 放到 PATH 前面，则应无 `WARN`、显示 `network-isolated`。

**可复用原则**：「能力不可用」与「断言失败」是两件事——前者该报告（WARN/说明），后者才是 FAIL；两者都不该静默。同类先例：输入缺失记 **GAP** 而不是静默 SKIP；且缺件的两种形态要分清（整个暂存目录缺失 = 一条 section 级 GAP 且逐组件断言不跑；目录在而单件缺 = 一件一条 GAP）。

## 3. 低占用源码构建：四轮才收敛

需要从源码构建外部组件时（正常路径是优先用官方预编译件，自建属例外），`-j` 不是唯一变量。实测收敛路径：

| 轮次 | 配置 | 观测 | 结论 |
|---|---|---|---|
| 1 | `-j 16` | 23 GB 宿主内存只剩 1 GB 可用，swap 吃掉 5–7 GB，两个 rustc 各 7.7 GB，load 17.3 | 会威胁同机常驻的其他 agent，**不可接受** |
| 2 | `-j 1` + `nice -n 19` | 单 rustc 仍爬到 6.5 GB 且继续涨 | 并行度不是唯一变量 |
| 3 | 再 + `OPENSSL_NO_VENDOR=1` | 不再从源码编 OpenSSL（原本在跑 `make build_libs`） | 砍掉一整块纯构建开销 |
| 4 | 再 + `CARGO_PROFILE_DEV_DEBUG=0` + 单前端线程 | 同一 crate 的中途快照读到 4.05 GB，其后实测涨到 7.42 GB | 方向对；但**峰值**才作数（见 §4） |

**五条可复用要点**：

1. **dev profile 默认带完整调试信息**；只需要一个能跑的二进制时它是纯浪费，而它是单个 rustc 峰值内存的大头之一。
2. **`OPENSSL_NO_VENDOR=1`**：系统装有 OpenSSL 开发件与 pkg-config 时，可直接绕开"从源码编 OpenSSL"。判定依据取自 `openssl-sys` 自身源码（该变量存在且不为 `0` 即不 vendoring），不是猜的。
3. **看门狗比"应该会轻一点"可靠**：另起一个进程定期检查 `MemAvailable`，低于阈值即中止构建，把预算变成**强制上限**，不让内核 OOM killer 去挑受害者。
4. **中断会让下一轮从头重编**（多次中断均观察到，`Compiling` 计数每次从 0 重新开始）⇒ 限流构建**不能靠反复打断来省资源**，打断反而是最费资源的操作。
5. **`nice -n 19`**：让位给同机其他 agent，长构建期间宿主仍可用。

## 4. 一条方法论教训

**单次 `ps` 快照不足以支撑「降到 X」这类结论**：同一个 rustc 进程中途读到 4.05 GB，几分钟后涨到 7.42 GB，基于快照写下的结论被自己的后续观测直接推翻。峰值必须由采样器（记录 RSS 高水位与可用内存低水位）给出。

同类既有教训一并留档：**源码 ≠ 产物**（判定外部工具行为要跑它自己的发布产物）；**缺工具链不是只能读源码的理由**（先查有没有官方预编译件）。

## 5. 生命周期与清理

- `.agent-scratch/external-test/`（沙箱跑者、暂存发布件、checkout）落在工作区内且已 gitignore ⇒ **没有任何机制会自动回收它**，保留是无限期的；将来要清必须**点名删除**。
- 放在 `/tmp` 的临时件由宿主规则按「30 天未访问」清理（本机确有该规则），**不需要**任何后续动作。
- 临时/一次性产物一律按显式文件名删除，不用通配符。
