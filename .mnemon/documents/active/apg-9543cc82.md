# APG 入口化与组件复用：本机组件库上线，身份可声明、依赖可检查（4.0.0）

状态：**契约已上线（ADR 0009 + 0010，D1–D11），第一个真实实例已建成并给出了有信息的判决，外部能力内部实测已做完并据此修掉四处真缺陷**。版本号 `4.0.0`（`d561a52` 抬版本，`a39c5a2` 补契约，`e6a7abf` 修路由），**标签 `v4.0.0` 故意未打**。本文是派生件，不是权威源：权威顺序 `decisions/0010` → `decisions/0009` → `plans/MULTI_AGENT_INFRA_INTEGRATION_RESEARCH.md` §13.20/§13.21（含 §13.21.5）→ 仓内代码与门禁。

## 1. 用户方向（原话要点）

- 先让 APG 住进去，再由 APG 把别的东西带进来（入口化）。
- **有些东西不用部署第二遍（HTTP），这种找已经有的**。
- 提前在本机单独找个地方摆好文件包 + HTTP 服务器，组织方式参考 APG 的部署方式。
- **各项目都尽量使用现成的，别到处都是**；对两个开口的裁定是「**都做**」。
- 「新的版本可以变成 **4.0** 开头了」；「在正式推广测试前先内部喊几个 agents」；随后纠正：**「不是评审，是对外部能力做测试」**。
- 「都修复一下，然后把**服务依赖的服务**也加入 APG 要求检查的东西，随后进一步处理，比较敏感的 root API 我自己来」。

## 2. 契约（ADR 0009 D1–D7；D2/D7 由 0010 细化与修订，0010 新增 D2a、D5–D11）

- **D1 落点** `<platformHomes(env).data>/components/`——`releases/` 的兄弟，沿用既有变量，不新增环境变量。
- **D2/D2a 引用与输出域** 项目只存引用；`verify` 报 `packages`/`packages_total`/`reusable_packages`/`missing_packages`/`degraded_packages`/`conflicted_packages`，`probe` 报 `probed`/`services`/`reusable_services`，**两个命令不得再发布同名裸 `reusable`**。
- **D3 两类条目** 包型 = `<id>/sha256-<hex>/` + 0444 canonical manifest（文件集须恰好相等）；服务型 = `services/<id>.json`，只记身份、不记字节。
- **D4 交付** `staged`（只验证/发现/复用，缺则 `not-installed`）／`fetched`（坐标供规程用，APG 不下载）；服务型只能是 `staged`。
- **D5 四态** `available`/`degraded`/`not-installed`/**`conflict`**；单例冲突 fail-closed，不替你挑。
- **D6 权限** 发现/校验/健康 = 只读；起停/重启/排空 = Operator + 确认 + 世代校验。
- **D7 分发面（已修订）** 校验与发现契约上分发面（`lib/components.mjs` + `schemas/component-entry.schema.json`，4.0.0 下 **85 文件 / `sha256:f4d86ec0…`**）；采集器 `scripts/build-component-store.mjs` **不上**。
- **D8 服务条目判据**：health 路径必须用**只读 GET** 返回 identity；端点必须**免凭据**可达；进程必须能被信号终止；`degraded` 永不算 `available`。实测下来三件在跑的服务一条都不满足（`am` 的 GET 只有 liveness，identity 在 MCP 握手；`ee` 要 token；`ft` 只有 metrics 且忽略 SIGTERM）。
- **D9 身份可声明**：service 条目可带 `identity: {id_field, revision_field}`（缺省即 `id`/`revision`），探针只读它声明的字段——这才让实测到的 `{service, rev}` 形状**能被诚实记录**。`asserted_identity: true` = 「在场但没人能核对是谁在应答」，**永远 `degraded`，绝不 `available`**；`stop: signal|sigkill` 记录确定性停止。
- **D10 依赖可检查**：包与服务都可带 `requires`，只允许三种**单键**要求——`{component: <id>}`（本 store 另一条目；`verify` 要求它真的验证通过，`probe` 只要求它存在）、`{bin: <name>}`（`PATH` 上且可执行）、`{env: <NAME>}`（**只判存在，从不读取/记录/返回值**）。**任一不满足 ⇒ `degraded` 并附未满足清单，永不算 `available`**。包的要求写在 manifest 里，因此**被 digest 覆盖**。只声明实测到的：`ntm`→`tmux`、`ft`→`wezterm`、`cass`→配套 `cass` CLI；`.beads` 目录、`slb` 的项目初始化、`sbh` 的 daemon+root、`cass` 的 API key 变量名**故意不猜**（`scripts/external-components.json` 的 `requires_note` 写明）。
- **D11 同一 id 两个 digest = `conflict`**：陈旧拷贝不得替组件回答问题，该 id 既不进 `reusable_packages` 也不进 `degraded_packages`（歧义本身就是结论），引用它的 requirement 不算满足；builder 只把残留报成 `stale` 并给**确切目录**，**自己不删**。

## 3. 第一个真实实例与版本记账

- 默认根 `~/.local/share/agent-project-guides/components`：9 件（`am`/`br`/`bv`/`cass`/`ee`/`ft`/`ntm`/`sbh`/`slb`）全部硬链接（同 inode、links=2，未复制第二份）。带要求重算后：`packages_total: 9`、**reusable 7 件**（`am`/`br`/`bv`/`ee`/`ntm`/`sbh`/`slb`）、**degraded 2 件并点名原因**（`cass`：`bin:cass` 不可用，其自身诊断也这么说；`ft`：`bin:wezterm` 不在 `PATH`）、`missing: []`、`conflicted: []`。第二次 builder 运行 `materialised 0 / present 9`。
- **仍无服务条目**（`services/` 不存在，`probe` 报 `probed: 0`）——D9 让「断言身份」可表达了，但**要不要为某个真实服务写下第一条，是主人的裁定**，不是实现细节。
- 4.0.0 四处一起动：`PACKAGE_VERSION`、`.agent-project-guides.json` 的 `provider.release`、根块（`reattest` 重盖章，integrity `24366bf1…`）、`PACKAGE_MANIFEST.json`。digest 本轮走了三步：`9791c583…`（抬版本时）→ `3c935f4b…`（组件契约）→ `f4d86ec0…`（路由词表），**始终 85 文件**。catalog 253 条内容不变（它编目路由条目，不编目路由文件哈希）。`project_digest` 随档案前移（`docs/memory` 的历史锚因此变旧，这是记忆锚拆分接受的语义，一条记录都没重写）。

## 4. 对外部能力的内部实测（三个 agent，只读优先）

团队 `apg-4.0.0-external-capability-test`：`cli-probe`（6 个 CLI 件）、`service-probe`（am/ee/ft）、`mcp-probe`（Bridge 控制面）。证据在 `.agent-scratch/capability-test-4.0.0/`（已忽略），摘要见 plan §13.21.3。

- **CLI：6/6 可执行，sha256 与采集记录逐位一致。** 缺的不是本地可执行性，而是外部上下文（`br`/`bv` 要 `.beads`、`cass` 要 API key、`ntm` 要 tmux、`sbh` 真回收要 daemon+root，**`sbh` 核心功能完全未验证**）。两条副作用：`slb check` 会写 `.slb/state.db`（**不是只读**，要用必须 `--db`/`-C` 指临时目录）；`cm ls` 会自动建空 playbook。
- **服务：「不用部署第二遍」在真机成立，但只有 `am` 干净**（`127.0.0.1:18765`，`/healthz`→`{"status":"alive"}`，`/health`→`{"status":"ready","version":"0.3.36"}`，`POST /mcp/` 握手回 `serverInfo{mcp-agent-mail,0.3.36}`）。按 D8 三件都不够格；D9 之后 `am` 这类可以用 `asserted_identity` **诚实**记成 `degraded`，但记录与否待裁定。
- **MCP：控制面活着，产品面在本会话不可达。** 本会话只有 `win-wsl-bridge-control` 的两个工具；`status` 显示 onshape/taobao 均 `running`/`mode:shared`（ownedGeneration 12 / 2，activeClients 各 2），但 `ownedGeneration`/`activeClients` 只是「已登记服务在跑且被共用」的**弱证据**，不能证明产品面可用、不能替代 store 的 identity+health 探针、不能排除 registry 外的第二份实例。
- **三条坑**：① 本环境 `http_proxy=127.0.0.1:10808` 且 curl 不认 `no_proxy` 里的 `127.*`，回环探测必须 `curl --noproxy '*'`，否则死服务返回 503 被读成活的（APG 自己走 `node:http`，不受影响）；② `ft watch` 收 SIGTERM 后不退出、且 `.ft/watch.lock` 挡住第二实例，只能 `kill -9`；③ `ft` 首次启动会往 `~/.local/share/fonts` 装 4 个 Nerd Font——**跑外部组件本身就可能改宿主**。

## 5. 实测与重算改掉的四处真缺陷（全部在打标签之前）

1. **`verify`/`probe` 曾各自发布同名的裸 `reusable`，指的是两个域**：读 `probe` 的 `reusable: []`（只可能来自服务）会得出「没有任何可复用组件」，而同一次 `verify` 报包全 `available`。现各报自己的域（`878f8d9`）。
2. **「200 但没有身份」曾报成 `the endpoint belongs to undefined`**（关于代码而不是关于组件的句子）。现在判 `conflict`，理由点名缺什么。**liveness 不是 identity**（`878f8d9`）。
3. **要求检查一度到不了 CLI 的判决**：`requires` 写在 manifest 里，而 store 遍历只返回 `{kind,id,digest}`，于是「缺可执行文件」的包仍被报成可复用。修复后遍历读回 manifest 的 `requires`，门禁红→绿（`a39c5a2`）。
4. **同一 id 出现两个 digest 时 `verify` 仍报可复用**：重算 manifest 时 `cass`/`ft`/`ntm` 换了 digest，旧目录留下，摘要把 id 列了两次。现在判 `conflict` 并点名两个 digest，builder 报 `stale` 且只给目录不删；三个陈旧目录已**按显式名字**删除，store 每 id 恰好一个 digest（`a39c5a2`）。

门禁 `scripts/test-component-store.mjs`：**64 条 → 103 条断言**（静态计数）。两条反证都跑过：把 `applyRequirements` 的降级分支短路 ⇒ 红在 `expected: 'degraded'`；把新增中文名词从 maintainer patterns 撤掉 ⇒ `test-v2` 红在 `actual: 'clarification_required'` vs `expected: 'ready'`。整轮 `scripts/test-release.sh` exit 0，boundary `10 groups, 85 files`，writers `69/0/1`。

## 6. 顺带收口：路由词表（建议信）与建议箱自身

- **建议信 0001**：中文**动作名词**任务一条规则都不命中，`落地主人裁定的13项并收口owner queue` 返回 `clarification_required`。信的提议（只往 `maintenance_delivery_patterns` 加词）**不够**——角色排序读的是 `roles[].patterns`，delivery 表只喂混合意图与否定判定。名词现在两处都进：maintainer ← `收口`/`收尾`/`补齐`/`整理`/`清理`，reviewer ← `复核`/`清单`，developer ← `新增`/`新命令`，delivery 表 ← 上述加 `落地`。**`落地` 刻意不进 maintainer 的角色 patterns**（它是 developer 那条 `落地修复方案` 的前缀，给了会把「把修复方案做出来」从 developer 抢走），门禁为此写了反向断言。改后该任务 `ready`/maintainer/code，7 条既有中文夹具全不变（含 `落地修复方案` 仍 `clarification_required`）（`e6a7abf`）。
- **建议信 0002**：`source-worktree` 仓里建议箱**没有被忽略**（排除只由 materializer 写进输出树，本仓从不经过它），于是「照政策写信」本身就脏了工作树。已采纳方案①：根 `.gitignore` 增 `.agent-project-guides/local/` 与 `.agent-teams/`，两者都**不在分发面**，85 文件与 digest 不受影响。两封信均已移入 `processed/` 并各附一行结论。
