# 第三方写入方门禁的验证设计与实测纪律（APG 3.0.10）

**这是派生件，不是权威源。** 权威顺序：`decisions/0006-root-instruction-block-ownership.md` → `plans/MULTI_AGENT_INFRA_INTEGRATION_RESEARCH.md` §13.18 → 仓内代码与测试。冲突时以仓内为准。

**与既有文档的分工**（它们讲"测了什么"，本文讲"怎么测才不算骗自己"）：

- `external-component-prebuilt-verify-…`（预编译件 fail-closed 校验 + 11 写入方 observed）：讲**安装与校验规程**。
- `apg-3-0-10-e25445ac`（宿主实务）：讲**沙箱失效判别与低占用构建**的宿主侧现象。
- `11-apg-3-0-10-7a28fea8`（普查）：讲**11 个写入方与守卫文法覆盖**。
- 本文：讲**证据分档、覆盖判定、空洞 PASS、测量纪律与可复现性**——即在写这些门禁时反复踩到、且换一个项目仍然会踩的那类错误。

## 1. 证据分四档，"真跑"不是二值

普查有 11 行，但"真跑"必须再分档，否则 `Evidence` 列写「scan + real run」时读者无法判断这行到底有多硬：

| 档 | 含义 | 现状 |
|---|---|---|
| ① 发布件真跑 | 驱动的是**用户会装到的那个件**（按 asset id 拉官方预编译件） | 8 个写入方 |
| ② 组件自己的脚本真跑 | 写入方**就是安装/生成脚本**，不跑脚本就碰不到写入路径 | 2 个（`ubs`、`acfs`） |
| ③ 仅源码（未跑） | 只读了源码、**没有任何执行证据** | **当前空置**（档位定义保留，供以后放真实状态，避免被迫冒充成已跑） |
| ④ 源构建后真跑 | 自己从源码构建再驱动 | 1 个（`ft`） |

- ④ 比 ①② 弱的地方**不在"是不是真跑"**（是真跑），而在**"跑的不是用户会装到的那个件"**。所以那类行应始终标注为「源构建 RC 证据」，**不得**被静默提升为"发布件已验证"。
- ① 是**唯一**"用户装到的东西"；②④ 都是真跑但同属次一档。
- ③ 空置是 11/11 全观测的记号，也是下面覆盖判定能定稿的前提。

## 2. 覆盖判定的分档依据：不是"有没有 marker"

把写入方按"有没有 marker"分档会得出错误的防御结论。真正决定防线的问法是：**marker 守卫能不能救它。**

| 档 | 判据 | 起作用的防线 | 剩余缺口 |
|---|---|---|---|
| **A 标记作用域内** | 只读写自己那对 marker，无人抢 byte 0 | 前缀 / 命名空间 / 恰好一次 / 完整性；端到端互操作测试 | 无 |
| **B 只追加、但恢复点不稳** | 追加，但备份拷贝发生在"已存在"检查**之前** | A 档那些仍成立 | 二次运行会用已改过的内容覆盖原始备份 ⇒「有备份」≠「能还原首次运行前」 |
| **C 整文件改写、marker 免疫** | 从不读 marker，整文件替换 | **marker 守卫在此档不可能生效**；只剩事后检测 + P8 恢复 | 顺序决定结果（见下） |

**C 档的三条要点**：事后检测（`install.sh check` 的 routing/trigger 校验）**只在事后**发现；P8 备份是唯一退路，而它之所以还在，是因为 APG 的备份后缀与所有写入方自己的备份名都不同；**顺序决定结果**——写入方在前、APG 在后，APG 重新占住前缀并把既有内容按字节与顺序下移；APG 在前、写入方在后，则 APG 区块被毁，只能靠备份还原（还原**对 APG 区块完整、对写入方内容有损**）。

**可复用判据**：一个"整文件改写"的写入方在守卫设计里**不能按 marker 处理**，也不能因为"它很少被运行"而降低标注等级。

## 3. 把"靠命名推断"换成实测

C 档唯一退路是那个 sibling 备份。最初的表述是"没有任何写入方用这个名字，所以整文件改写不会覆盖它"——**这是从命名推出的，不是观测**，而 C 档全部期望都压在这一条上。

改成可执行断言：先按真实后缀埋一份 sibling 备份，跑完整文件改写，再断言它**逐字节不变**。两条通过（`ntm setup --force`、`cass project --force`，后者实测根文件 2,094 B → 261 B、APG 区块清零、备份完好）。

**关键纪律：三行里只测了两行，就写"2/3"。** 第三行（`acfs`）靠的是"shell `>` 只指向一个目标路径"这一机制性论据，因此被**明确标为推断而非实测**，不与前面两条混在一起。把"2/3"写出来比把三行都写成一个语气更值钱。

## 4. 空洞 PASS 的四种形态（本文最该被复用的部分）

"断言通过"与"断言是有效的"是两件事。写 ft 那段断言时连续造出四处空洞 PASS，**每一处都是"断言在什么都没发生的情况下也会通过"**：

| 形态 | 它是怎么空过的 | 修法 |
|---|---|---|
| **A 前置目录缺失** | 建了 home 目录却漏了工作目录，埋种子的 `cp` 直接失败；被测程序于是走"新建文件"分支，而断言仍在"文件已存在"的前提下解读 | 补齐目录；并让断言在文件不存在时**FAIL** |
| **B 对不存在的文件取文本再哈希** | 从不存在的文件里 `sed` 抽取区块，前后两次都取到空串，两个空串哈希相等 ⇒ "区块逐字节不变"**通过** | 先断言"抽取结果非空"，取不到就判 FAIL 并说明"这条比对是空洞的" |
| **C 快照命名把文件当目录用** | 快照把 `seed/a` 先写成文件、再想把它当目录（`seed/a/b`），后几级快照**静默没生成**，递归断言拿不存在的路径去比 | 快照名扁平化（`seed-a`、`seed-a-b`…），并要求快照**确实存在**，否则 FAIL |
| **D "没有变化"型断言** | 幂等、不递归、区块未被改动——这些在"什么都没干"时**恒为真** | 全部绑定一个 `wrote` 前置条件：第一次写入确实发生**且文件确实变长**，否则判 FAIL |

**总原则**：**"文件没有变化"型断言必须绑定"变化确实发生过"的前置条件。** 否则任何静默什么都不干的实现（插件、封装脚本、feature 未编入的构建）都能拿满分——而"静默什么都没干"恰好是最常见的真实失败形态，不是角落情况。

**配套做法：留一个可执行的负控制。** 把被测二进制换成 `/bin/true`，断言它**必须产生 N 个 FAIL**（本例 9 个）。这样"这些断言会咬人"本身变成可随时重跑的证据，而不是评审时的口头保证。同理，"拒绝路径"也必须配一个"旧算法确实会犯错"的对照，否则"拒绝有效"不可证。

## 5. 测量纪律：四个会让人写出错误结论的陷阱

1. **同名不同值会让人用错参照。** 记忆子系统的锚是 `projectDigest(descriptor) = sha256(canonicalJson(descriptor))`，而 `project validate` 输出的 `project_digest` 是**另一个值**。照着后者的数字去比对记忆记录，会得到错误的相符/不符判定。本例"用错参照但结论侥幸不变"（两个历史值与两个候选参照都不等），但那是运气，不是方法。**用参照值前先确认它是哪个东西算出来的。**
2. **单次快照不能支撑"降到 X"这类结论。** 依据一次 `ps` 快照写下"降到 4.05 GB"，几分钟后同一进程涨到 7.42 GB，最终真实峰值比初稿高三倍。凡是用 `ps` 采样，先确认单位（把 KB 当 MB 打印会输出 `13551040 MB`，数字真、单位错），并只信**全程采样得到的峰值**，不信任何单点。
3. **"有多大"要先看是不是同一个东西。** 一个"自身 2,063 B vs 消费方 731–758 B"的对比，实际是**两套不同模板**（一个是常驻教义块、另一个是生成式路由块），据此得出的"该瘦身多少"是错位的。**量差异之前，先确认两边是可比的同类。**
4. **对照窗口只能提示"有新写入"，不能独立归属。** 逃逸检测靠"窗口内新增文件 − 对照窗口背景"做集合相减，但背景写者在不同轮次会变；某一轮里出现在逃逸列表中的仓库路径，其实是**我自己在探针运行期间编辑文件**。所以归属仍需人知道自己在干什么，**不能报成"干净"**。

## 6. 可复现性：配方与产物的生命周期

- **`/tmp` 按年龄清理，所以要留在仓内的是"配方"而不是"目录"。** 本机由 `/usr/lib/tmpfiles.d/tmp.conf`（`D /tmp … 30d`）按 **30 天年龄**清理，与是否重启无关；只存在于 `/tmp` 的构建脚本与二进制会一起消失，实测就再也复现不了。**收敛后的确切配方（含每个环境变量的理由与源码 commit、工具链溯源）必须落进仓内文档**，`/tmp` 只当缓存。
- **保留产物、丢构建中间件**：先 `cp` 出二进制并**验证副本能跑**（版本输出与构建一致），再按**显式名**删除构建树（本例 17 GB 纯中间件）。结果：宿主磁盘 10 GB 可用 / 90% 满 → 27 GB 可用 / 72%，而产物仍在。删除**只用显式名，不用通配符**。
- **小清单可以替掉大依赖**：一份 **1,921 B** 的溯源清单（仓 + tag + asset id + 归档/二进制双 sha256 / HEAD commit）替代 **554 MiB** 暂存件 + 数 GB checkout。这是"删掉暂存区不等于让门禁静默退化"的前提；但"清单存在"与"清单被跟踪"是两件事，后者属新增被跟踪文件。
- **校验和一致 ≠ 构建溯源。** 多来源校验和即使全部一致，也不覆盖"这个产物是从那段源码构建出来的"。该缺口要**明写为未执行**，不能让上面的数字把它盖住。
