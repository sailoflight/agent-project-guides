# APG 4.x：多入口、可组合的 AI 开发基础设施方案

日期：2026-09-23。状态：**用户已确认多入口、独立管理和 APG 最终退出管理入口的产品方向；以下仍为待实现设计，不替代现行 ADR**。
依据：`APG_V4_BOUNDARIES_AND_PROJECT_SPLIT_REVIEW.md` 及其固定上游来源记录。

本方案修正上一轮可能被误解为“所有运行必须经过 APG/能力宿主”的目标图。用户明确：APG 不必是唯一入口；应补齐现有生态没有满足的需求，而非将其全部收归 APG。进一步澄清：APG 是可信的本地孵化载体，外部能力管理项目成熟后，APG 可以移除管理入口，成为独立治理 CLI（按此前约定将 CIL 理解为 CLI）。

## 1. 架构决定

采用**多入口、职责分离、公开接口组合**，而非以 APG 为中心的必经控制面。

- 人类、agent 客户端、NTM、已有 CLI 或未来项目看板均可作为入口。
- APG 是项目治理与上下文组件。孵化期可以承载外部能力接入；成熟后将基础设施管理职责及其入口交给独立管理项目，不保留永久转发义务。APG 治理 CLI 仍可被任何已接入入口调用。
- 已有后端负责实际任务存储、调度、会话、通信、检索及资源机制。
- 能力管理是独立产品边界，负责基础设施选择、安装计划、配置、检查、更新、停用/卸载及实例管理；尽量委派已有实现，不默认建成常驻进程、全局执行代理或第二套通用包管理器。
- 跨项目应用和架构导航按独立产品边界设计，但仅在复用验证后决定是否另建仓库。
- 不采用中央消息总线、统一业务数据库或所有工具必须依赖的新 SDK 作为第一阶段前提。

这里的“补缺”是补齐我们已经证明的需求缺口；不能从 APG 没接入，推断作者整个生态没有相应功能。

## 2. 目标拓扑

```text
人类 / agent 客户端 / NTM / 原生 CLI / 项目看板
             多个独立入口，按任务组合
    ┌────────────────────────────────────┐
    │ 项目治理：APG                     │
    │ 角色/模式、内容、版本、物化、晋升  │
    ├────────────────────────────────────┤
    │ 基础设施管理：独立管理 CLI         │
    │ 选择、安装/配置、检查、更新与移除  │
    ├────────────────────────────────────┤
    │ 执行与领域后端：复用已有项目       │
    │ 任务 / 会话 / 邮件 / 检索 / 审批  │
    └────────────────────────────────────┘
旁路：项目组合视图、架构导航、证据摘要
```

这是职责图，不是每次调用都必须按层经过的请求链。允许入口直接调用后端；也允许后端的集成适配器请求 APG 上下文。APG 的缺席不应让非 APG 项目无法使用原生工具。

## 3. 产品边界与不做什么

| 单元 | 核心职责 | 明确不做 | 初始交付位置 |
|---|---|---|---|
| APG Core | 项目治理、角色/模式、精确上下文、版本锁定、物化/迁移、正式知识晋升 | 不成为唯一入口；不拥有通用调度器/终端/任务或向量库 | 现有 APG 仓库 |
| Capability Manager（工作名） | 选择基础设施、依赖/版本/作用域计划、安装/配置、检查、更新、停用/移除；服务生命周期委派对应后端 | 不重写成熟安装器/doctor；不接管 agent 任务调度或工具私有业务数据库 | 先在 APG 内孵化清晰边界；成熟后独立项目/CLI，APG 退出管理入口 |
| Workspace View（工作名） | 多项目身份、Git/任务/治理/运行状态的组合视图，显式委派初始化和推进 | 不复制 br 数据库、NTM 调度器或 ru 同步机制 | 先验证 ru/bv/ntm 组合；有缺口才做薄应用 |
| Architecture Navigator | 模块职责、源码定位、流程图、变更影响与测试入口 | 不自建全语言语义引擎；不把声明图当运行证明 | 保持作者工具，第二个项目验证后再独立 |
| 运行后端 | 自身领域操作及生命周期 | 不因被集成而自动取得其它系统的权威 | 外部项目，按需使用与固定版本 |

角色路由暂不单独成项目：先分离纯决策和 IO；正式内容闭包、预算、目标绑定和票据仍由 APG 维护。APG 项目角色与后端 agent/model 选择是不同路由问题。

## 4. 对现有生态的复用与缺口分类

重新核对的 NTM 固定版本 README 已声明 deps、编排、工作图、审批、checkpoint/pipeline 等；repo_updater 固定快照声明多仓同步、状态及 agent 工作流。它们是文档支持范围，不替代本地验收。

据此，需求分成三类：

1. **已有机制，直接复用**：任务事实、会话编排、邮件、检索、原生依赖诊断、多仓同步等。不另造实现。
2. **已知集成缺口，我们补接线**：按项目固定 APG 版本；将项目治理接入不同入口；按构建/操作判定 readiness；跨来源显示可追溯状态。
3. **尚未证明的生态缺口，先验证**：跨项目自治推进、人机架构导航的通用能力、统一恢复等。先看已有工具能否满足验收，不能先贴“作者缺失”的标签。

若上游已满足某接口/场景，适配器应删减而不是保留第二份实现。上游功能重叠时按项目/会话选主后端，不把所有组件同时启用视为集成成功。

## 5. 能力管理的产品边界与首个切片

最终范围包含**基础设施选择与生命周期管理**，而非仅一个检查器。实施先做跨工具检查和计划，再接安装/变更；这是交付顺序，不是永久排除安装能力。管理器不全面取代上游安装和诊断机制。

- 查询上游原生 deps/doctor/status，保留原始来源、时间、版本、错误与未知态。
- APG 已有制品摘要验证继续作为独立证据；上游自报健康不能替代它。
- 区分 installed、executable、configured、reachable、compatible、operation-ready。授权结果与健康分开，不用一个全局布尔值混合所有维度。
- 前提按 operation + backend + build 选择，例如 cass-memory 的 playbook 与历史检索、ft 的诊断与具体 mux 操作。
- 配置补全先生成计划：将改哪些路径、作用于机器还是项目、是否可回退；然后显式批准和验证。
- 安装由选定 provider 执行，是管理器的正式职责：复用安装渠道，核实许可证/来源/版本；不隐式执行整栈安装器，不在健康检查里安装或修复。检查与安装具有不同副作用，不能共享一个含糊的 auto-fix 开关。
- 目标配置记录所需能力、选定 provider、精确版本/制品、机器/用户/项目作用域；观测记录与目标配置分离。发现的已有工具先标为外部管理，不自动接管。更新锁定规则、卸载所有权和共享使用者必须明确；没有引用记录不证明无人使用。
- 基础服务启停可委派 system service/原生工具；agent session/job 调度仍属 NTM 等后端。管理器安排“铺什么、怎么维护”，不重复安排“每个 agent 下一步做什么”。
- 调用适配优先适用于已证明的协议差异。入口可直接调用后端，不能为了“统一”强制增加代理 hop。
- 对同一组件的直接访问和 NTM 内部集成，使用可核对的 provider/instance 身份关联，不启动重复实例。

第一阶段默认按需运行，无常驻守护进程。用户可信本地环境中采取与实际副作用相称的约束，不扩张为企业权限平台。

## 6. 多入口下的契约与证据

先定义少量逻辑数据契约，尽量映射现有 JSON，不要求上游改协议，也不新建独立 protocol 仓库。

| 契约 | 最小内容 | 所有者 |
|---|---|---|
| ProjectContext | 项目/工作区身份、APG 精确版本、角色/模式、上下文来源摘要、治理要求 | APG；由入口适配器获取 |
| CapabilityStatus | provider/instance、版本/构建、操作、状态、原因、观测时间及证据 | 能力检查组件，标明原始来源 |
| ExecutionReceipt | 后端任务/attempt 标识、项目、使用的上下文引用、结果、验证与日志引用 | 执行后端/入口适配器；不强制 APG 新建任务库 |

长任务的 job/attempt、暂停/恢复、取消、预算与租约，优先使用选定后端已有机制。我们只映射其真实语义；缺少的能力报告 unsupported/unknown，不用包装层虚构 exactly-once 或可靠恢复。

治理接入的建议路径：入口在任务开始/切换时请求项目 pinned APG 的上下文；适配器交给 agent，记录来源；执行仍在原后端；完成时关联验证与必要的知识提案。

**不能把路径约定当成强制安全边界**：

- 直接从原生 CLI 启动而未接入治理的任务可以存在，但不能标成“已按 APG 验证”。
- 上下文生成/交付不证明模型实际遵循。
- 对指定为“必须治理”的任务，已接入入口在获取必需内容失败时停止该任务；不能声称这能阻止系统上所有其它入口。
- 真实权限由宿主、用户和执行工具约束；APG 与能力检查结果都不自授权限。

## 7. 单一事实来源与故障隔离

- 治理与正式项目规则：项目 canonical 文件及其固定 APG 内容。
- 任务：选定 tracker（如 br），不另建看板私有任务真相。
- 会话：选定 runtime（如 ntm 或相应终端后端）；同一会话只有一个生命周期管理者。
- 记忆：检索/经验是候选资料；正式项目知识由明确晋升流程形成。
- 组件：后端拥有自身配置/状态，检查组件拥有登记和派生观测，不穿透修改私有数据库。
- 多项目看板只存登记、偏好、观测缓存和证据引用；不上升为所有业务状态的中央数据库。

看板故障不影响原生 CLI；导航故障不影响 context；可选后端缺失不阻断无关操作；必须的治理版本缺失只使相应受治理任务显式失败。过期、不可访问、未安装和失败必须区分。

## 8. CODE 母目录的交付范围

默认显式登记或受限发现，识别路径、Git common-dir/worktree 与实例，避免 symlink 重复和误接管；非 Git/非 APG 项目仍可列入。

1. 只读：展示 Git、任务、运行、APG 固定版本、能力及最后验证状态；不因扫描自动 fetch、安装或初始化。
2. 初始化：委派现有骨架/环境工具；选择接入 APG 的项目才走其 preview/apply。
3. 推进：在具名任务、预算、批准、隔离和停止条件明确后委派后端；不因人工离线自行扩权。

对 ru/bv/ntm 的复用验收不满足时，只实现差额；不要把“我们需要看板”推导为“我们需要另一套全栈调度器”。

## 9. 实施顺序、验收与兼容

1. **契约修订**：将已批准方向反映到 ADR/公共边界及测试；方案文本本身不改变现行行为。
2. **最小互操作切片**：同一个 APG 项目，从 APG CLI 和非 APG 入口分别取得等价治理上下文；能力检查只读；已选、许可明确的后端完成一个低风险任务；证据可关联而无重复实例/任务库。
3. **能力适配**：逐个补构建/操作级依赖、配置计划、调用结果。区分已发现、已检查、已适配、已实测，不把所有条目标为支持完成。
4. **CODE 只读视图**：复用现有后端；3.x、4.x、无 APG 项目并存，不修改被观察项目。
5. **独立与退出**：管理项目验证独立安装/运行、迁移与非 APG 入口后独立交付；按第 11 节让新版 APG 退出管理入口。导航按复用需求独立；角色路由暂留核心。自治推进最后验收。

每阶段独立 commit。额外反例：上游缺失/协议漂移、诊断命令意外写入、任务开始后状态变旧、上下文未接入、版本缺失、取消失败、直接/嵌套访问同一实例。状态检查不是永久有效的执行许可。

保护 3.x：不覆盖全局入口，不广播迁移，不更改其它项目 pin；开发入口和可写状态隔离；复用制品须验证；跨版本适配不支持时报告不支持，不回退 latest。迁移期间维持仍受支持 APG 版本的 `components verify|probe` 契约；成熟后的新版可以显式移除，无须永久 façade。旧版运行时及其私有状态不得随之删除或重写。

## 10. ACFS 管理能力：已有实现，选择性复用

只读核对固定提交 `b042ffba3b6f874db0608c8171a42c577bdc2f1f`，不声称它是当前最新版本；来源哈希见 `APG_INFRA_MANAGEMENT_ACFS_SOURCES.json`。

| 已有机制 | 源码/文档证据 | 管理项目的采用判断 |
|---|---|---|
| 模块目录、依赖、安装/验证声明 | `acfs.manifest.yaml` | 借鉴/映射已有清单，不手抄第二份全栈安装脚本 |
| 模块/阶段选择及执行计划 | `install.sh` 声明 `--only`、`--only-phase`、`--skip`、`--print-plan` | ACFS provider 候选；先验收选择是否真的约束全部副作用，不能仅看参数名 |
| 分类更新、诊断、版本 hold | README 的 Update Command、Per-Tool Version Holds | 可复用；hold 的期限及忽略行为不等于 APG 精确版本锁，需明确转换 |
| 二进制 smoke check 与 `.prev` 恢复 | README 的 Post-Install Verification and Rollback | 仅采纳它实际保证的恢复范围，不扩大为整机/数据库事务回滚 |
| 部分服务 status/start/stop/restart | `scripts/lib/acfs-services.sh` | 适配已有服务管理，不推断为所有 provider 的统一生命周期 |
| 通用卸载、跨工具事务回滚 | 本次材料未完成相应验证 | 保持 unknown/unsupported，不承诺全支持 |

ACFS 不是默认安全的“只装一个工具”函数。此提交 manifest 涉及系统包、用户/sudo 配置和工作目录；README 描述 Ubuntu 自动升级及宽范围 update。它与现有开发机的目标可能不同。

采用策略：优先作为**可替换、选择性启用的 provider**；若 ACFS 已能满足某类机器的整栈需求，管理项目只做目标/状态适配，不再造安装器。对于现有开发机，先使用明确的用户级/固定版本渠道；整机 provisioning 单独批准。不要把 `--only` 或 `--dry-run` 当作已经证明无越界副作用。

本地可信 APG 可减少不必要的分布式安全复杂度，但不消除系统升级、共享实例删除、第三方许可和版本兼容等实际边界。固定提交 LICENSE 含前述附加限制，未将“可参考的技术设计”当作已获得安装/运行/再分发许可。

## 11. APG 退出管理入口的生命周期

### 阶段 A：本地孵化

APG 暂时承载接入入口与实测；新管理代码不得依赖 APG 的角色/内容编译内部实现，路径、store、命令执行和网络接口从边界注入。既有组件检查契约保持不变。

### 阶段 B：独立管理 CLI

管理项目能在没有 APG 的机器/项目中单独运行。APG 的管理命令只作为过渡适配，不复制新实现。管理项目可把 APG 当作一种可安装的基础设施，但项目治理版本仍由项目 pin 决定，不能借管理更新自动改 pin。

### 阶段 C：新版 APG 移除管理命令

- 有明确版本的弃用/迁移说明，不在补丁更新中静默删除公共行为。
- 新入口、记录迁移、旧入口行为和回退路径均有 fixture 与实际切片证据；共享实例与外部管理工具不会被自动接管/删除。
- 不动其它仓库固定的 3.x/4.x 运行时；历史版本继续按原契约运行。兼容的对象是具体受支持版本，不是永久保留所有历史命令。
- 新版 APG 保留治理、context、物化/迁移与正式知识等职责；移除基础设施管理，不缩减成只输出角色名称的脚本。
- 已安装 APG 的正常 context/治理操作不依赖管理器在线。缺少固定版本时明确失败，由用户/上层入口安排安装，不隐式 latest 或自动引导整套管理器。

最终依赖方向：上层入口可以分别调用管理 CLI、APG CLI 和执行后端；管理器可安装指定 APG 制品；APG 的日常治理运行不反向硬依赖管理器。避免引入互相启动才能运行的循环。

## 12. 本次变更范围
